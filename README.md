# depgraph

Builds a bidirectional, file-level import/export dependency graph for a
codebase mixing Java, Python, JavaScript and TypeScript. Uses
[tree-sitter](https://tree-sitter.github.io/) to parse each file (no
`node`, `python`, or `javac` execution involved — everything is static).

## Usage

```sh
cargo build --release
./target/release/depgraph build <dir> <output>
./target/release/depgraph show <output> <file>
```

Two files, two jobs:

- **`<output>.graph.json`** — pure structure, fully regenerated by every
  `build`. A deterministic function of the source tree: same input,
  same output, no merge logic, safe to overwrite wholesale.
- **`<output>.ctx.json`** — a sidecar with human/LLM-authored notes
  (see [Context annotations](#context-annotations)). `build` never
  reads or writes it. It only ever holds files someone actually
  annotated, so it stays small no matter how large the repo is.

`<output>` is a base name: `depgraph.json` and `depgraph` both produce
`depgraph.graph.json` (and, once something's annotated, `depgraph.ctx.json`).

```sh
depgraph build ./my-project ./depgraph
depgraph show ./depgraph src/lib/index.ts
```

`show` prints one file's node from `graph.json`, merged with its note
from `ctx.json` if there is one — so you (or an LLM) never have to load
the whole graph just to look at one file. `file` can be the full
relative path or just a unique trailing suffix of it (`Button.tsx`,
`components/Button.tsx`); if that's ambiguous, `show` lists every match
so you can be more specific.

### `build` flags

- `--compact` — write compact JSON instead of pretty-printed.
- `--with-external` — keep `external_dependencies` (npm/stdlib/JDK
  packages) on every node. Off by default.
- `--with-barrels` — keep barrel files (pure re-export files, e.g. an
  `index.ts` that only does `export * from './x'`) as nodes, along
  with `is_barrel`/`effective_dependencies`/`effective_dependents`.
  Off by default: barrels are dropped and every remaining node's
  `dependencies`/`dependents` are rewired to skip straight through to
  the real files that used to sit behind the barrel, so `b` importing
  `foo` from a barrel `a/index.ts` that re-exports it from `a/foo.ts`
  shows `b` depending directly on `a/foo.ts` — no `index.ts` node in
  the output at all.

  The default, in other words, is already "just files with real code,
  and how they actually connect." Pass both flags if you want the full
  picture including barrels and third-party packages.
- `--exclude <glob>` — skip files/directories matching this
  gitignore-style glob, relative to `dir`. Repeatable:
  `--exclude '**/*.test.ts' --exclude 'legacy/**'`. On top of whatever
  `.gitignore` already excludes and the always-skipped directories
  below.

## What gets scanned

Extensions: `.java`, `.py`/`.pyi`, `.js`/`.jsx`/`.mjs`/`.cjs`,
`.ts`/`.mts`/`.cts`/`.tsx`.

`.gitignore`/`.git/info/exclude` rules are respected, hidden files/dirs
are skipped, and these directories are always skipped regardless of
`.gitignore`: `node_modules`, `dist`, `build`, `out`, `target`, `.next`,
`.nuxt`, `__pycache__`, `.venv`, `venv`, `env`, `.mypy_cache`,
`.pytest_cache`, `.tox`, `coverage`, `vendor`, `.idea`, `.vscode`,
`.gradle`, `.settings`, `.git`. Add more with `--exclude` (see above).

## Output schema

`<output>.graph.json`:

```jsonc
{
  "root": "/abs/path/to/scanned/dir",
  "generated_at": "2026-09-23T17:41:57Z",
  "nodes": {
    // default (no --with-barrels/--with-external): barrels already
    // collapsed, so this file wouldn't even appear as a node -- shown
    // here with both flags on, to illustrate every field.
    "src/lib/index.ts": {
      "hash": "e9ff2d870f7e925e",   // content hash, for change detection
      "is_barrel": true,            // re-exports only, no local exports
      "exports": ["OTHER", "*"],    // "*" = wildcard/unknown-name export
      "dependencies": ["src/lib/impl.ts", "src/lib/other.ts"],
      "dependents": ["src/consumer/main.ts"],
      "effective_dependencies": ["src/lib/impl.ts", "src/lib/other.ts"],
      "effective_dependents": [],
      "external_dependencies": []   // unresolved: npm/stdlib/etc packages
    }
  }
}
```

All paths are relative to `root`. Resolution is **file-level, not
symbol-level**: an edge means "this file imports/re-exports something
from that file," not "this exact imported name exists there." There's
no `language` field — it's already implied by the path's extension.

`is_barrel`, `effective_dependencies`, `effective_dependents`, and
`external_dependencies` only appear at all under `--with-barrels`/
`--with-external` (see [`build` flags](#build-flags)); by default
they're omitted, not just empty.

- `dependencies` / `dependents` — direct edges. Under `--with-barrels`
  this includes barrel files (a barrel's own dependents are whoever
  imports *the barrel*, not who imports the things it re-exports);
  without it, barrels are gone and these are already the "effective" view.
- `effective_dependencies` / `effective_dependents` (only with
  `--with-barrels`) — the same, but walked through any `is_barrel`
  files to the underlying non-barrel source. Answers "what does this
  file *really* depend on" / "who *really* depends on this file"
  through re-export chains (JS/TS barrel `index.ts` files, Python
  `__init__.py` re-exports).
- `is_barrel` (only with `--with-barrels`) — true if the file has
  re-exports (`export * from`, `export {x} from`, or for Python, an
  `__init__.py` that does `from .submodule import X`) and no exports
  of its own.
- `exports` — best-effort list of exported/public names. Java: public
  top-level type names. Python: `__all__` if present, else top-level
  `def`/`class`/assignment names. JS/TS: declared/re-exported names;
  `"*"` means "everything, but we don't track exact names" (wildcard
  re-exports, `module.exports = {...}`, `from x import *`).

## Context annotations

`<output>.ctx.json` is a flat, sparse map — only files someone actually
annotated appear in it at all:

```jsonc
{
  "src/lib/index.ts": {
    "ctx": "Public barrel for the lib package.",
    "ctx_hash": "e9ff2d870f7e925e"   // graph.json's hash for this file
                                     // at the time ctx was written
  }
}
```

`depgraph build` never reads or writes this file. Fill it in by hand,
or point a (cheap — the notes are meant to be short, "what it does, not
how") LLM at each file's contents and have it write `ctx` + `ctx_hash`
(`ctx_hash` = that file's current `hash` from `graph.json`) for
whichever paths it's covering. `depgraph show <output> <file>` reads
both files and reports `ctx_stale: true` whenever `ctx_hash` no longer
matches the file's current `hash` in `graph.json` — that's computed at
read time, not stored, so annotating (or re-annotating) a file is just
one write to `ctx.json`, nothing else to keep in sync.

## Resolution notes & limitations

- **JS/TS**: relative imports (`./`, `../`, and root-relative `/`) are
  resolved on disk trying `.ts .tsx .js .jsx .mjs .cjs .json` and
  `index.*`. If the specifier itself already has a `.js`/`.jsx`/`.mjs`/
  `.cjs` extension but no such file exists, its TS-source equivalent is
  tried too (`.ts`/`.tsx`/`.mts`/`.cts`) — the standard pattern under
  `moduleResolution: bundler`/`nodenext`, where you write the *emitted*
  extension (`import './foo.js'`) even though the source is `./foo.ts`.
  `require()`, dynamic `import()`, and basic CommonJS (`module.exports`,
  `exports.x`) are all picked up alongside ESM `import`/`export`.

  Barrel re-exports are resolved **per imported name**, not per file:
  if `a/index.ts` does `export * from './foo'; export * from './baz'`,
  then `import { FOO } from 'a'` resolves through to `a/foo.ts`
  specifically and `import { BAZ } from 'a'` to `a/baz.ts`, rather than
  both fanning out to everything the barrel re-exports. This falls back
  to the barrel's *entire* surface (still correct, just less precise)
  whenever a name can't be narrowed: namespace imports (`import * as
  ns`), `require(...)`/dynamic `import(...)` (their destructuring isn't
  tracked), or a re-exported name whose own source file's exports
  aren't fully enumerable (e.g. it re-exports from an external package,
  or does `module.exports = {...}`).

  Bare specifiers (`import { foo } from 'a'`) are first checked against
  every `package.json` found under the scanned root (skipping
  `node_modules`) — so in a monorepo, `import { foo } from 'a'`
  resolves to sibling package `a`'s entry point (via its `exports`/
  `main` field, or `index.*`/`src/index.*` if neither is set), and a
  subpath import like `import x from '@scope/a/utils'` resolves the
  same way against `@scope/a`'s `exports` map or `utils.*` on disk.
  Anything that doesn't match a local package name (`react`, `lodash`,
  etc.) is still external. There's no `node_modules` resolution for
  *non-workspace* packages.

  `tsconfig.json`/`jsconfig.json` path aliases are also supported: for
  a bare specifier, the nearest enclosing config (walking up from the
  importing file) is checked first — `compilerOptions.paths` patterns
  (exact or single-`*`-wildcard, longest-prefix-wins on ties), then a
  plain `baseUrl`-relative fallback if no pattern matches — before
  falling back to workspace-package lookup, then external. `extends`
  chains are followed (relative, or into `node_modules` for shared
  base configs), and configs are parsed leniently (`//`/`/* */`
  comments and trailing commas are stripped before JSON parsing).
- **Python**: the scanned directory is assumed to be on `sys.path`
  (i.e. it's your project's import root — point `depgraph` at `src/`,
  not its grandparent, if that's where imports resolve from). Handles
  absolute and relative imports, packages (`__init__.py`) vs. plain
  modules, and `from pkg import name` where `name` is either a
  submodule or an attribute re-exported by `pkg/__init__.py`. Stdlib
  and third-party imports are always external (no `site-packages`
  resolution). Unlike JS/TS, re-exports through `__init__.py` are not
  yet resolved per-name — importing two different names re-exported by
  the same `__init__.py` will currently show both importers depending
  on everything that `__init__.py` re-exports, not just the specific
  name each one uses.
- **Java**: resolution is index-based — every `.java` file's `package`
  declaration and top-level type names are scanned first, then imports
  are matched against that index. Only types declared inside the
  scanned directory resolve internally; JDK/library imports
  (`java.util.List`, etc.) are always external. Nested/inner classes
  aren't indexed individually, only top-level types.
- Import cycles are handled (visited-set guards in the barrel-following
  BFS), but genuinely circular *effective* dependencies will just show
  up as edges in both directions rather than being flagged specially.

## Project layout

- `src/walk.rs` — directory walk + language detection.
- `src/lang/{java,python,js_ts}.rs` — per-language extraction +
  resolution, each producing a common `FileFacts` (`src/facts.rs`).
- `src/lang/js_pkg.rs` — indexes local workspace `package.json` files so
  bare-specifier imports (`import x from 'a'`) can resolve to sibling
  monorepo packages instead of always being treated as external.
- `src/lang/ts_paths.rs` — indexes `tsconfig.json`/`jsconfig.json`
  `compilerOptions.paths`/`baseUrl` so aliased bare-specifier imports
  (`import x from '@app/foo'`) resolve too.
- `src/graph.rs` — cross-file assembly: reverse edges, barrel-following/
  -dropping. Pure function of the scanned files; no I/O beyond reading
  source.
- `src/model.rs` — the JSON schemas (`Graph`/`Node` for `graph.json`,
  `CtxEntry`/`CtxStore` for `ctx.json`).
- `src/main.rs` — the `build` and `show` subcommands, and the
  `<output>` → `(<output>.graph.json, <output>.ctx.json)` naming
  convention.
